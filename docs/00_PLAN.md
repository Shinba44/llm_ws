# マスタープラン

> 目的: 特定個人に常駐し、対象を解析し、能動的に通知してくるパーソナルLLMエージェントを自作する。
> 同時に、LLMの内部構造を手を動かして理解する。

関連ドキュメント:
- [01_SETUP.md](01_SETUP.md) — 環境構築（**cloneしたらまずここ**）
- [02_AGENT_SPEC.md](02_AGENT_SPEC.md) — エージェントの設計仕様
- [03_PROGRESS.md](03_PROGRESS.md) — 進捗ログ（**作業再開時はここを読む**）
- [04_RESOURCES.md](04_RESOURCES.md) — 学習リソース
- [05_FIELD_VISUAL.md](05_FIELD_VISUAL.md) — 解析フィールドの視覚仕様（A5のUI）

## 1. 基本方針: 2トラック並走

| | トラックA「作る」 | トラックB「学ぶ」 |
|---|---|---|
| 目的 | 動くエージェント | LLMの中身の理解 |
| 手段 | 既存モデル（API / ローカル）の上に構築 | スクラッチ実装・自前学習 |
| 成果 | 日常的に使えるツール | 「なぜ動くか」の説明能力 |
| ペース | 早く動かす。完成度は後回し | 急がない。理解優先 |

**なぜ並走か**: トラックBだけだと成果物が出ずモチベーションが切れる。トラックAだけだと
「APIを叩くだけの人」で終わる。AでモチベーションとゴールイメージをキープしつつBで中身を掘る。

**合流点**: 最終的に「**トラックBで自分がファインチューンしたモデルが、トラックAのエージェント基盤の上で常駐して動く**」状態を目指す。これが本プロジェクトのゴール。

```
   Track A  A0 ──> A1 ──> A2 ──> A3 ──> A4 ──> A5 ──> A6
            推論基盤              \              /
                                   \           /     ← M3で合流
   Track B  B1 ──> B2 ──> B3 ──> B4 ─> B5 ─> B6 ──> B7
                                        FT（必須）
```

A0（ローカル推論基盤）が全体の土台。B6でファインチューニングしたモデルを
A0の基盤に載せ替えることで、2つのトラックが1つの動くものに合流する。

## 2. マイルストーン

| ID | 内容 | 完了条件 | 目安 |
|---|---|---|---|
| **M0** | 基盤整備 | `pixi run -e gpu gpu-check` が通り、テストが走る | 1日 |
| **M1** | ローカルモデルと会話できる | 自分のGPUで動くモデルとCLIで対話できる。**口調は崩れてよい** | 1〜2週 |
| **M2** | 記憶と知識を持つ | 過去の会話を覚え、自分の資料を検索して答える | 3〜4週 |
| **M3** | 口調が安定する | FTしたモデルが定型フォーマットを守る。**ここで初めて完成形になる** | 1〜2ヶ月 |
| **M4** | 常駐エージェント | 常駐して能動的に通知してくる | 2〜3ヶ月 |

> 期間は「週末エンジニアリング」を想定した目安。厳守しない。

**M1とM3の役割分担が本計画の要**。M1では小型モデルが `解。` を守りきれない。
それを承知で先に進み、M3のファインチューニングで解決する。
これによりトラックBが「学習のための課題」ではなく「動くものを作るための必須工程」になる。

## 3. Phase 0: 基盤整備（M0）

- [x] `pixi.toml` の作成（環境: `default` / `laptop` / `gpu`）
- [x] `.env.example` を用意
- [x] `ruff` + `pytest` を feature に登録、タスクを定義
- [ ] ディレクトリ構成の確定（§6）
- [ ] GPUマシンでの動作確認（`pixi run -e gpu gpu-check`）
- [ ] `nvidia-smi` の CUDA Version を見て、`pixi.toml` のwheel indexを確定する
      （[01_SETUP.md](01_SETUP.md) §4.3）

### なぜ pixi か

このプロジェクトは**Pythonだけで完結しない**。

| フェーズ | 非Python依存 |
|---|---|
| A5 常駐オーバーレイ | Node.js（Electron採用時） |
| **B7 量子化・高速化** | **cmake + C++コンパイラ**（llama.cpp のビルド） |
| B3 学習 | CUDA Toolkit |

pixi はこれらを1つのlockfileで管理でき、マシンごとの差異を `[environments]` で
切り替えられる。複数マシンをまたぐ本プロジェクトの前提に合う。

## 4. トラックA: エージェント構築

> **本プロジェクトは商用APIを使わない。推論はすべて自分のGPUで完結させる。**
> 理由と帰結は §9 を参照。

### A0. ローカル推論基盤 【M1】
**最初にこれを立てる。** 以降のすべてのフェーズがこの上に乗る。

- [ ] Ollama もしくは llama.cpp server をGPU機に立てる
- [ ] OpenAI互換エンドポイント（`/v1/chat/completions`）として叩けることを確認
- [ ] VRAMに応じたモデル選定（§7-2）
- [ ] 量子化レベル（Q4_K_M / Q6_K / Q8_0）で日本語品質と速度を実測して比較する
- [ ] tokens/sec とVRAM使用量を記録する（常駐に耐えるかの判断材料）

**学べること**: 量子化のトレードオフ、推論サーバの運用、VRAM管理

> もともとB7にあった内容の前倒し。APIを使わないなら、これが**前提条件**になる。

### A1. 対話CLI + ペルソナ定義 【M1】
最初の動くもの。「自分のGPUで動くエージェントと話せる」状態にする。

- [ ] LLMプロバイダ抽象化（Ollama / llama.cpp server / 将来のFT済みモデルを差し替え可能に）
- [ ] システムプロンプト設計（→ [02_AGENT_SPEC.md](02_AGENT_SPEC.md)）
- [ ] 応答フォーマットの強制: `解。` `告。` `是。` `否。` `提。` のプレフィックス
  - [ ] まずプロンプトだけで試し、**どのくらい守られないかを実測する**
  - [ ] 制約付きデコーディング（GBNF文法 / JSON schema）を導入する
  - [ ] それでも残る崩れは後処理で吸収する
- [ ] ストリーミング出力 + リッチCLI（`rich` / `prompt_toolkit`）
- [ ] 会話履歴の保持（セッション内）

**学べること**: プロンプトエンジニアリング、**制約付きデコーディング**、
小型モデルの指示追従の限界、トークン管理

> **重要**: ここで口調は完全には安定しない。それでよい。
> 「プロンプトだけでは守れない」ことを数字で確認しておくと、M3のFTの意味がはっきりする。
> 遵守率を記録して [03_PROGRESS.md](03_PROGRESS.md) に残すこと。

### A2. 解析・検索（RAG） 【M2】
「対象を解析して根拠付きで情報を返す」というエージェントの中核機能。

- [ ] ドキュメントローダ（md / pdf / txt / ソースコード）
- [ ] チャンク分割戦略の比較（固定長 / 意味的分割）
- [ ] 埋め込みモデル（日本語対応: `multilingual-e5-*` / `ruri` 等）
- [ ] ベクトル検索を **まず自前のnumpyで実装**（学習目的）→ 後で `chromadb` / `faiss` に置換
- [ ] ハイブリッド検索（BM25 + ベクトル）とリランキング
- [ ] 出典表示（根拠を必ず示す）

**学べること**: 埋め込み空間、コサイン類似度、検索の失敗パターン、コンテキスト設計

### A3. 取り込みと永続メモリ 【M2】
取り込んだものを蓄積し、次に活かす。

- [ ] 会話ログのSQLite永続化
- [ ] 長期メモリ: 事実の抽出・保存・想起
- [ ] コンテキスト長超過時の要約圧縮
- [ ] 取り込みコマンド: URL/ファイルを与えて知識化する

**学べること**: コンテキストウィンドウ管理、要約戦略、メモリアーキテクチャ

> ローカル小型モデルは要約が苦手。**要約プロンプトは短く単純に**保ち、
> 抽出したい項目を構造化出力（JSON schema）で指定して品質を補う。

### A4. 外部情報アクセス（ツール利用） 【M2〜M3】
**トラックAの最難関。** ローカル小型モデルのtool callingは商用APIほど安定しない。

- [ ] ツール群: Web検索、ファイル読み書き、シェル実行、Python実行
- [ ] Tool calling の実装。**2案を比較する**
  - [ ] ネイティブのtool calling対応を使う（Qwen3 など対応モデルが必要）
  - [ ] ReActをテキストとして自前パースする（モデルを選ばない。文法制約と併用）
- [ ] ツール呼び出しの失敗率を測り、リトライ・自己修正を入れる
- [ ] 危険な操作の確認プロンプト（暴走させない）

**学べること**: エージェントループ、ツールスキーマ設計、エラーリカバリ、
**弱いモデルで動かすための設計**

> ここで詰まったら、より大きいモデル（VRAMが許す範囲で）に上げる、
> あるいはツール選択だけをFT対象に加える、という手がある。

### A5. 常駐と能動通知 【M4】
本エージェントの一番の特徴。**聞かれていないことを自分から言ってくる**。
視覚表現の仕様は [05_FIELD_VISUAL.md](05_FIELD_VISUAL.md)（参照実装あり）。

- [ ] バックグラウンド常駐プロセス（systemd user unit / デーモン）
- [ ] イベント監視: ファイル変更、Gitリポジトリ、カレンダー、CI、RSS
- [ ] トリガ条件の判定
- [ ] デスクトップ通知（`notify-send`）/ 通知の抑制ルール
- [ ] 定型文: `告。<事象>を検知しました。<提案>`
- [ ] モデルを常駐させるか、必要時にロードするかを決める（VRAM占有とのトレードオフ）

**学べること**: イベント駆動設計、常時稼働システムの運用

> **ローカル完結にした最大の恩恵がここ。** API課金がないため、
> 「毎回LLMを呼ばない設計＝コスト対策」という制約が消える。
> 気の済むまで推論を回してよい。制約はVRAMと電力だけ。

### A6. 並列処理（マルチエージェント） 【M4以降・任意】
- [ ] 非同期タスク実行（`asyncio`）
- [ ] サブエージェントへの委譲と結果統合
- [ ] バックグラウンド解析タスク

> ローカルではVRAMがボトルネックになる。並列に見せかけつつ実際は
> 単一モデルへのバッチ推論に落とす設計が要る（B4のKVキャッシュ理解と直結）。

## 5. トラックB: LLMの中身

> **原則: ライブラリを使う前に、必ず一度は自分で書く。**

### B1. トークナイザ自作
- [ ] 文字レベル → 単語レベル → **BPEをスクラッチ実装**
- [ ] 日本語での挙動確認（バイト単位BPEの必要性を体感する）
- [ ] `tiktoken` / HF `tokenizers` と結果を比較

### B2. Transformer スクラッチ実装
- [ ] Self-Attention を数式から実装（QKV, スケーリング, マスク）
- [ ] Multi-Head Attention
- [ ] Positional Encoding（絶対位置 → **RoPE**）
- [ ] LayerNorm / RMSNorm、残差接続、FFN（SwiGLU）
- [ ] デコーダのみのGPTブロックを積む

**チェックポイント**: Attention の計算を紙に書いて説明できるか

### B3. 学習ループ
- [ ] データセット準備（TinyShakespeare → 日本語小コーパス → 青空文庫）
- [ ] 学習ループ、損失関数（クロスエントロピー）
- [ ] AdamW、学習率スケジュール（warmup + cosine）
- [ ] 勾配クリッピング、勾配累積、混合精度（AMP / bf16）
- [ ] TensorBoard or `wandb` でロス可視化
- [ ] チェックポイント保存・再開

**GPUマシンでの目標**: 10M〜100Mパラメータのモデルを実際に事前学習して、
それらしい文章が出るところまで持っていく。

### B4. 推論の実装
- [ ] 貪欲法 / temperature / top-k / top-p / repetition penalty
- [ ] **KVキャッシュ**の実装と速度比較
- [ ] バッチ推論
- [ ] （余裕があれば）投機的デコーディング

**チェックポイント**: KVキャッシュありなしで何倍速くなったか、なぜ速いか説明できるか

### B5. スケールと現実
- [ ] スケーリング則（Chinchilla）を読む
- [ ] 自分のGPUで何パラメータまで学習可能か計算する（VRAM見積もり式）
- [ ] 「事前学習は個人には無理」の具体的な数字を把握する
- [ ] → だからファインチューニングをやる、という納得を得る

### B6. ファインチューニング 【M3・トラック合流点】★必須工程
**このプロジェクトで最も重要なフェーズ。** A1で判明した「口調が守られない」問題を
ここで解決する。やらなければエージェントは完成しない。

- [ ] ベースモデルの選定（A0で実測した候補から。§7-2）
- [ ] SFT用データ作成: **ペルソナに沿った応答例を数百件**（→ [02_AGENT_SPEC.md](02_AGENT_SPEC.md) §2.4）
- [ ] LoRA / QLoRA でファインチューニング（`peft` + `trl`）
- [ ] **A1で記録したプレフィックス遵守率と比較する**。改善が数字で見えること
- [ ] GGUF変換 → A0の推論基盤に載せ替える ← **ここで合流**
- [ ] 差し替え前後でエージェントの挙動を比較

### B7. 量子化と高速化の深掘り 【A0の続き】
基礎はA0で済んでいる。ここではより踏み込む。

- [ ] 量子化手法（Q4_K_M / Q6_K / Q8_0 / imatrix）による劣化を定量評価
- [ ] `llama.cpp` を自分でビルドしてオプションを変える（`native` featureが要る）
- [ ] `vLLM` との比較（スループット重視の構成）
- [ ] FT済みモデルを常駐に耐えるレイテンシとVRAMに収める

### B8. アラインメント基礎（任意）
- [ ] RLHF / DPO の概念を読む
- [ ] DPOを小規模データで試す

## 7. ハードウェア戦略

作業マシンは複数ある想定。各マシンの実測値は [01_SETUP.md](01_SETUP.md) のマシンプロファイル表に記録する。

### 7-1. 用途別の要件

**API課金がない代わりに、GPUがすべての前提になる。** GPU機が本プロジェクトの本体。

| 用途 | 必要なもの | 代替 |
|---|---|---|
| **A0（推論基盤）** | **GPU必須。VRAM 8GB〜が現実的** | 量子化すればCPUでも動くが実用速度は出ない |
| A1〜A6（エージェント開発） | 推論基盤にネットワーク越しに繋げばよい | ノートPCから GPU機の Ollama を叩く |
| B1, B2, B4（実装・理解） | CPUで十分。小さいモデルで動作確認 | — |
| B3（事前学習） | GPU推奨。VRAM 8GB〜 | Google Colab / Kaggle（無料T4） |
| B6（ファインチューニング） | VRAM 8GB〜（QLoRAなら6GBでも可） | Colab（無料T4でも1〜3Bなら可） |

> ノートPC（GPUなし）からGPU機の推論サーバをLAN越しに叩けば、
> 開発はノートPCでもできる。`.env` の `AGENT_BASE_URL` を向け先に設定する。

### 7-2. VRAM別のスコープ目安

| VRAM | A0 常用モデル | B3 事前学習 | B6 ファインチューニング |
|---|---|---|---|
| 〜6GB | Qwen3 4B Q4 | 〜30Mパラメータ | 0.5〜1B QLoRA |
| 8〜12GB | **Qwen3 8B Q4 / Gemma 3 12B Q4** | 〜150Mパラメータ | 1〜3B QLoRA |
| 16〜24GB | Qwen3 14B〜32B Q4 | 〜500Mパラメータ | 7〜8B QLoRA |
| ノートPC(CPU) | Qwen3 0.6B〜1.7B Q4 | — | — |

**A0とB6のモデルサイズを揃えなくてよい。** A0で大きいモデルを常用しつつ、
B6では小さいモデルをFTして「自分で育てたモデル」として比較する、という進め方も有効。

日本語重視なら Sarashina / Swallow / llm-jp も候補。A0で実際に喋らせて選ぶ。

**重要**: 重みとデータはGitに入れない（`.gitignore`済み）。マシン間の移動は
「再取得スクリプト + HuggingFace Hub」で行う。学習済みチェックポイントを共有したく
なったら HF Hub にプライベートリポジトリを作る。

## 9. ローカル完結の方針

**本プロジェクトは商用LLM APIを使わない。推論はすべて自分のGPUで行う。**

### 帰結

| 項目 | 影響 |
|---|---|
| コスト | ゼロ。常駐して回し続けても課金されない |
| プライバシー | 個人データが外部に出ない。パーソナルエージェントとして本来こうあるべき |
| レート制限 | 存在しない。A5の能動通知と相性が良い |
| **モデル性能** | ⚠️ **落ちる。指示追従が弱い** |
| **B6の位置づけ** | ⭐ **任意課題から必須工程へ** |

### なぜこれが計画として良いのか

商用APIを使う場合、`解。` の口調はシステムプロンプトだけで守れてしまう。
つまりB6のファインチューニングは「やってもやらなくてもよい学習課題」だった。

ローカルの小型モデルは口調を守りきれない。だからB6が**動くものを作るために必要な工程**になる。
トラックAとトラックBの合流が、名目上ではなく実質を伴う。

### 新たに必要になる技術

APIを使っていたら学ばずに済んだが、実務価値の高い項目。

1. **制約付きデコーディング** — GBNF文法、JSON schema。弱いモデルに形式を守らせる
2. **量子化の実測** — Q4とQ8で日本語品質がどう変わるかを自分で測る
3. **推論サーバの運用** — 常駐、VRAM管理、モデル切り替え

### 例外的にAPIを使ってよい場面

**B6のSFTデータ合成のみ**、無料枠のあるサービス（Google AI Studio 等）を使ってよい。
数百件の生成なのでレート制限にかからない。エージェント本体の常用には使わない。

プロバイダ抽象化（A1）を作っておけば、この切り替えは設定1行で済む。
